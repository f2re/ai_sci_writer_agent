# Методы и архитектура аргумента

Применить корневой `AGENTS.md`. Получить бриф, проверенный корпус, evidence, тезаурус и доступные данные.
Прочитать схемы data-manifest/results; использовать `docs/artifact-examples.md` только как пример формата.

## Выход

Подготовить `research-plan.md`, `analysis/analysis-plan.md`, `analysis/data-manifest.json`,
`analysis/results.json`, фактические `analysis/logs/` и `outline.md`.
Для неприменимых собственных результатов сохранить пустой results и содержательное not_applicable_reason.

## Дизайн и анализ

1. Связать вопрос с оцениваемой величиной/отношением, единицей анализа и областью вывода.
2. Выбрать описательный, ассоциативный, причинный, теоретический или обзорный тип основания.
3. Проверить достаточность данных, происхождение, период/пространство, отбор, пропуски и единицы.
4. Зафиксировать критерии, baseline, альтернативные объяснения, неопределённость и чувствительность.
5. Различить exploratory и confirmatory. Подтверждающий план зафиксировать `freeze-plan` до результата.
6. Локальная фиксация — хеш и время; не называть её внешней предрегистрацией или доказательством приоритета.
7. Выполнить реальный анализ; сохранить версии, команды, code_paths, время и фактические логи.
8. Проверить отрицательные результаты и условия применимости; не скрывать их для удобства сюжета.

Данные регистрировать с ID, kind, provenance и файлами/хешами. Каждый R-результат содержит
value, unit, kind, dataset_ids, command, executed_at, log_path/log_sha256, analysis_plan_sha256.
Учитывать зависимости наблюдений, утечку данных, пространственную/временную структуру и
множественные сравнения по применимости. Не заменять величину эффекта одним p-value.
Результаты моделирования отделять от наблюдений; графики строить из фактических данных.

## Теория, обзор и протокол

Для теории явно задать посылки, области переменных, переходы, контрпримеры и граничные случаи.
Стороннюю теорему оформить source, свой вывод — inference с основаниями.
Для обзора выбрать тип синтеза, критерии поиска/отбора, сопоставимость работ и ограничения покрытия.
PRISMA и другие reporting guidelines применять по дизайну, не ко всем жанрам автоматически.
Протокол описывает будущую работу; ожидаемые результаты не записывать как полученные.

## Архитектура статьи

Для каждого раздела записать вопрос, функцию, разрешённые C/R-ID, таблицы/рисунки и границы вывода.
Проверить цепочку «вопрос → метод → результат → интерпретация → ограничение → вклад».
Распределить объём по реальным требованиям журнала; сумма бюджетов должна укладываться в общий лимит.
Структуру выбирать по жанру; IMRaD и пять заголовков не обязательны для любой работы.
Не планировать новый результат, которого нет в evidence/results. Сильнейшее возражение отразить в обсуждении.

## Завершение

Писатель получает цель каждого раздела и допустимую силу утверждений; рецензент — материал для проверки.
Если метод/данные изменились, сохранить решение и повторить затронутые этапы, не переписывая историю.
